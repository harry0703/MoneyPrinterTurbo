# Default container image: Trivy review, 2026-10-29

The deployed CPU image was scanned by digest with Trivy 0.74.0, using the
2026-10-29 vulnerability database and HIGH/CRITICAL severities:

```text
ghcr.io/harry0703/moneyprinterturbo@sha256:100b3d24eade1e62785a8a3165c83d10b2d12114c18e191ab5f9a91eeb4716a0
```

The complete package/advisory list, including versions, fix availability and
links, is [trivy-2026-10-29.csv](trivy-2026-10-29.csv). Its `before` and `after`
rows are raw finding counts, with no advisory suppression. These counts are
package/advisory pairs, not unique CVEs. The same CVE can affect several FFmpeg
libraries. The baseline has 176 distinct advisory IDs; the rebuild has
44.

## Remediation

- Move the Python 3.11 CPU image from Bullseye to Trixie, update the mirror
  suites together, and apply available distribution updates during builds.
  Publishing pulls the current base image. Debian documents Trixie's supported
  lifecycle in its [release information](https://www.debian.org/releases/trixie/).
- Upgrade FileLock to >=4.2.1, LiteLLM to 1.103.1, python-multipart to 0.0.30
  and Starlette to 1.3.1. Update Streamlit to 1.66.1 for the patched media stack
  and Pillow 13 support. Keep the requirements file and project lock aligned.
- Install Pillow >=13.0.0,<14, which resolves all 40 Pillow findings in this
  scan, including five critical findings. MoviePy 2.2.1's published metadata
  caps Pillow below 12. Use an explicit uv dependency override rather than
  silently retaining the vulnerable Pillow release. Keep MoviePy's public
  version and the package's pip-compatible dependency metadata intact.
- Refresh setuptools and wheel in the container to versions at or above their
  required safe versions (82.0.1 and 0.46.2). This also replaces the vulnerable
  `jaraco.context` copy vendored by the older base image's setuptools.
- Add a container security workflow on dependency changes and weekly. It saves
  every high/critical finding as an artifact and fails on those with an
  available fix; unfixed findings remain visible in the complete report.

The non-Pillow Python advisories in the baseline are CVE-2026-112940
(FileLock), GHSA-g5ff-637f-6q2m (LiteLLM), CVE-2026-53539
(python-multipart), CVE-2026-54283 (Starlette), CVE-2024-6345 and
CVE-2025-47273 (setuptools), and CVE-2026-24049 (wheel).

### Installation and rebuild

`uv sync --frozen` applies the project override automatically. To install from
the requirements file with the same security override:

```sh
uv pip install --overrides requirements-security.txt -r requirements.txt
docker build --pull --no-cache \
  --build-arg DOCKER_BUILD_MIRROR=default \
  --build-arg PIP_USE_OFFICIAL=1 -t mpt:security .
trivy image --scanners vuln --severity HIGH,CRITICAL mpt:security
trivy image --scanners vuln --severity HIGH,CRITICAL \
  --ignore-unfixed --exit-code 1 mpt:security
```

The updated LiteLLM release also fixes CVE-2026-114612; setuptools >=82.0.1
removes its vulnerable vendored jaraco.context copy (CVE-2026-23949) and updates
its vendored wheel copy. Installing a fixed standalone wheel alone does not
replace the embedded copy.

Plain `pip install` does not implement uv overrides and will still obey
MoviePy's Pillow<12 cap. The Pillow remediation therefore applies to the
container and the documented uv installation paths. Ordinary pip/PyPI
installations need a future MoviePy metadata fix or the explicit uv override.
Because the override intentionally exceeds MoviePy's declared cap,
`pip check` can report that cap as a conflict; media compatibility is checked
with actual rendering tests instead of claiming the upstream metadata changed.

## Validation

- The clean linux/amd64 production image builds successfully. Its final Trivy
  scan reports no high/critical Python findings and no fixable high/critical
  findings; the remaining distribution findings are listed above.
- The updated uv lock scan analyzes 122 package entries with no high/critical
  findings. `uv lock --check` and Ruff pass.
- The full Linux suite passed 3,024 tests and 12,878 subtests, with 19 skips.
  Three tests initially failed because Streamlit now resolves relative
  `AppTest.from_file` paths against the calling test file. Those tests now use
  absolute paths; the affected modules and packaging tests pass in a separate
  final run: 44 passed. The full suite was not repeated after the path-only fix.
- A separate native FFmpeg rendering/output-container run passes all 57 tests.
- The attempted Windows full run could not collect native CTranslate2 tests
  because a required DLL was unavailable on the host. Linux provides the full
  runtime validation above; Windows and arm64 results remain for upstream CI.
