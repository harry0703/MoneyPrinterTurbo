# Фото-вставки из локальной папки

Наложение фотографий пользователя на сильные фразы сценария. Фича выключена по
умолчанию (`photo_enabled = false`), поведение пайплайна без неё не меняется.

Дата разработки: 2026-08-13.

---

## Зачем

Тот же приём, что и GIF-вставки (`gif-overlays.md`), но с собственным контентом:
скриншоты, продукты, кадры — то, чего нет в стоковых каталогах. Источник —
локальная папка, поэтому ни внешнего API, ни ключей не нужно.

Отличия от гифок, зафиксированные осознанно:

- **Показ короткой вспышкой** (`photo_duration`, деф. 2.0 сек ± 0.5), а не всё окно
  фразы: статичное фото дольше не живёт, начинает читаться как зависший кадр.
  Джиттер детерминированно выводится из имени файла.
- **Анимация появления обязательна** — статичной картинке нужен вход, иначе она
  выглядит как склейка. Пул из трёх дешёвых анимаций, без per-frame поворотов.

## Поток данных

```
сценарий → озвучка → субтитры (или gif-timeline.srt из TTS-таймингов)
   ↓
generate_photo_overlays()          окна ((start, end), текст)
   ↓
llm.generate_photo_moments()       один вызов LLM: индексы сильных строк
   │   фолбэк: _spread_photo_moments() — равномерно по ролику
   ↓
фото из photo_dir по порядку имён → [{path, start, end}]
   ↓
video.generate_video(photo_overlays=[...])
   ↓
_build_photo_overlay_clips() → CompositeVideoClip поверх гифок и субтитров
```

Тайминги переиспользуют гифочный код (`_gif_timeline` / `_subtitle_windows`):
окна из SRT, без субтитров — временный SRT из TTS-таймингов, без таймингов —
вставки не добавляются.

## Как выбираются моменты

`llm.generate_photo_moments()` получает пронумерованные строки и возвращает
json-массив индексов (`[0, 4, 9]`) — искать нечего, поэтому query нет. Правила в
промпте те же, что у гифок: конкретика или эмоция, разброс по ролику, меньше —
нормально. Нормализация выкидывает дубли и выходы за диапазон.

Если LLM не дал ничего — `_spread_photo_moments()` раскладывает фото равномерно
по ролику. Гифкам такой фолбэк не положен (без query нечего искать), фото он
подходит: контент уже на диске.

Фото назначаются выбранным строкам **в порядке сортировки имён файлов**;
`amount = min(photo_amount, файлов, окон)`. Хочется управлять порядком — префиксы
`01-`, `02-` в именах.

Если файлов в папке больше, чем вставок, `_select_photos()` берёт их равномерно по
всему списку, а не первые `amount` подряд: иначе тема, которая по алфавиту идёт
последней, молча не попадала бы в ролик ни разу. Индексы моментов сортируются, так
что порядок фото на экране совпадает с порядком имён.

## Показ и анимации

Начало — старт фразы; длительность `photo_duration ± 0.5` сек (джиттер
детерминирован именем файла), обрезается концом таймлайна. Окна субтитров бывают
короче показа фото, поэтому старт сдвигается за конец предыдущей карточки —
иначе при плотной раскладке (десятки вставок на минуту) карточки наезжали бы друг
на друга. Раскладка карточки — целиком гифочная (`_gif_overlay_placement`):
чередование сторон, наклон к центру, разброс по высоте, скругление, тень.

Анимации (`photo_animation`, деф. `random` — детерминированный выбор из пула по
имени файла):

| Анимация | Что делает | Механика |
|---|---|---|
| `pop` | scale 0.85→1.0 за 0.35 с, ease-out | `resized(λt)` + позиция с фиксированным центром |
| `slide` | въезд со стороны размещения | `with_position(λt)` от -w / video_width |
| `kenburns` | зум фото 1.0→1.10 внутри карточки всё время показа | inner `resized(λt)` в `CompositeVideoClip` фиксированного размера |

Плюс кросс-фейд 0.25 с на входе и выходе у всех.

Ключевое отличие от гифок по стоимости: для `pop`/`slide` карточка (фото со
скруглением + тень + наклон) **запекается один раз в PIL** в единую RGBA-картинку —
`_photo_card_image()`; per-frame `vfx.Rotate` не используется. PIL `rotate()`
крутит против часовой на положительном угле, как и `vfx.Rotate`, поэтому знак
угла общий. `kenburns` внутри окна анимирует контент, поэтому идёт гифочным путём
(маска + `vfx.Rotate` на карточку и тень); inner-зум стартует с 1.0 и только
растёт — рамка всегда покрыта, подмена маски безопасна.

Анимация `tilt` (доворот на место) отложена сознательно: это per-frame поворот с
переменным углом, дороже всего пула вместе взятого.

## Конфигурация

`VideoParams` (ключей в `config.toml` нет — источник локальный). Из CLI —
`--photo-enabled/--no-photo-enabled`, `--photo-dir`, `--photo-amount`,
`--photo-size`, `--photo-duration`, `--photo-animation`; несуществующий `--photo-dir`
отбрасывается ещё argparse'ом, до создания задачи.

| Поле | Деф. | Что делает |
|---|---|---|
| `photo_enabled` | `false` | вкл/выкл фичу целиком |
| `photo_dir` | `""` | папка с jpg/jpeg/png/webp |
| `photo_amount` | `5` | максимум вставок (1–40) |
| `photo_size` | `0.42` | доля ширины кадра (0.1–0.9) |
| `photo_duration` | `2.0` | средняя длительность показа, сек (0.8–6.0) |
| `photo_animation` | `"random"` | `random / pop / slide / kenburns` |

## Поведение при сбоях

Единственный жёсткий отказ — в preflight: включённая фича с пустым/несуществующим
`photo_dir` или папкой без картинок валит задачу **до** трат на LLM и TTS
(`_validate_photo_overlay_params`, только для `stop_at in (materials, video)`).
Дальше — тихая деградация, ролик собирается без фото:

| Ситуация | Что происходит |
|---|---|
| Папка опустела между preflight и рендером | лог + пустой список |
| Нет таймингов (нет SRT и sub_maker) | вставки не добавляются |
| LLM вернул мусор | нормализация чистит, до 5 ретраев, потом равномерный фолбэк |
| Битый файл картинки | ловится в цикле `_build_photo_overlay_clips()`, остальные рендерятся |
| EXIF-поворот телефонных фото | `ImageOps.exif_transpose()` перед рендером |

## Ограничения и открытые вопросы

1. **Гифки + фото одновременно**: моменты размечаются двумя независимыми вызовами
   LLM, вставки могут совпасть по времени и месту. Пока считаем, что включают
   что-то одно; при реальном спросе — общая разметка одним вызовом.
2. **Порядок фото** — только сортировка имён; сопоставления «фото ↔ смысл фразы»
   нет. Возможное развитие — LLM матчит по именам файлов.
