# Непрерывный фон из одного длинного видео

Фон ролика — один непрерывный отрезок, вырезанный со случайного места длинного
исходника и обрезанный по центру под формат кадра. Фича выключена по умолчанию
(`continuous_background = false`), поведение пайплайна без неё не меняется.

Дата разработки: 2026-08-13.

---

## Зачем

Для «геймплейного» фона (паркур в Minecraft, subway surfers и прочий залипательный
loop) нарезка из множества коротких клипов работает против формата: картинка дёргается
каждые 5 секунд, хотя нужен ровно обратный эффект — непрерывное движение, на фоне
которого читается озвучка.

Штатный путь `combine_videos` для такого исходника даёт два неподходящих результата:

- `sequential` — из-за `break` в нарезке берутся только первые `max_clip_duration`
  секунд файла, дальше они зацикливаются на всю длину ролика;
- `random` — весь файл режется на куски по `max_clip_duration`, они перемешиваются, и
  фон скачет между разными местами исходника.

Плюс общий для обоих режимов: горизонтальный исходник вписывается в вертикальный кадр
**с чёрными полями** (масштабирование до `1080x607` по центру `1080x1920`), а не
кропается.

---

## Как работает

```
длительность озвучки + 0.1s запаса
   ↓
выбор исходника: только те, что не короче нужной длины
   ↓
случайная стартовая точка внутри исходника
   ↓
один вызов FFmpeg: crop (центр, под соотношение кадра) → scale → fps
   ↓
combined-*.mp4 — дальше обычный generate_video (субтитры, озвучка, BGM)
```

Точка входа — `app/services/video.py::combine_videos`: при `continuous_background=True`
управление уходит в `_build_continuous_background` до того, как начнётся нарезка на
подклипы, и функция возвращается сразу после успешной записи файла.

### Кроп, а не чёрные поля

`_center_crop_geometry` считает наибольший центральный прямоугольник исходника, у
которого уже нужное соотношение сторон. Для `1920x1080` → `1080x1920` это
`608x1080+656+0`: полная высота, срезаны бока. Размеры принудительно чётные — `yuv420p`
не принимает нечётные.

Порядок `crop → scale` важен для скорости: обратный порядок (сначала растянуть кадр,
чтобы он покрыл рамку, потом обрезать) заставляет ресемплить 6.5 Мпикс на кадр вместо
0.6 Мпикс.

### Почему FFmpeg, а не MoviePy

Первая версия резала и кропала через MoviePy — 5-секундный фон собирался 57 секунд,
почти всё время уходило на пофреймовый resize в Python. Один вызов FFmpeg с фильтром
делает то же самое за 3 секунды; минута фона — около 82 секунд.

Ещё 3.5x дал `-preset veryfast`: этот файл всё равно перекодируется на финальном
рендере, поэтому качество промежуточного артефакта не критично. Пресет добавляется
**только для `libx264`** — у аппаратных кодеков (`h264_nvenc` и прочие) свои имена
пресетов, и чужое имя уронило бы кодирование.

Скорость (2.6 ГБ исходник, 3 часа, 1080p60 → 5.1 с вертикального фона):

| вариант                        | время |
| ------------------------------ | ----- |
| MoviePy, scale → crop          | 57 с  |
| MoviePy, crop → scale          | 29 с  |
| FFmpeg, пресет по умолчанию    | 21 с  |
| FFmpeg, `-preset veryfast`     | 3 с   |

### Скорость воспроизведения

`clip_speed` учитывается на входе: из исходника читается `нужная_длина * скорость`
секунд (`-ss`/`-t` **до** `-i`, чтобы FFmpeg не декодировал пропускаемую часть), а
`setpts=PTS/скорость` сжимает таймлайн обратно до длины озвучки.

## Фолбэки

Оба ведут к штатной нарезке-склейке, задача не падает:

- **нет исходника нужной длины** — например, озвучка на 60 с, а самый длинный материал
  40 с. Резать нечего: фон оборвался бы на середине;
- **FFmpeg вернул ненулевой код** — ошибка логируется, `_build_continuous_background`
  возвращает `False`.

---

## Ограничения

- Работает от длины **одного** файла. Склейка нескольких длинных исходников в один
  непрерывный фон не поддерживается — это уже другой режим.
- Итоговый fps — общий для модуля `fps = 30`; 60fps исходник теряет половину кадров.
- Из исходника берётся только видео (`-an`): звук геймплея в ролик не попадает.
