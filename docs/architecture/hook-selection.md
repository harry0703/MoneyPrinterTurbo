# Выбор хука: генератор кандидатов + скорер

`docs/playbook/hooks.md` требует, чтобы первая строка производилась отдельным шагом:
сценарный генератор не имеет права мимоходом сочинить вступление. Здесь этот шаг.

Дата разработки: 2026-08-12.

---

## Где живёт

```
app/services/hooks.py     промпты, валидация, разбор ответов (провайдера не знает)
        ↓
app/services/llm.py       generate_hook(): два вызова провайдера
        ↓
app/services/task.py      шаг перед генерацией сценария
```

`hooks.py` держит реестр из 12 классов (`HOOK_CLASSES`) и детерминированный фильтр;
`llm.py` — единственное место, где эти промпты уезжают в провайдера. В `task.py`
провайдер по-прежнему не протекает.

## Как работает шаг

1. **Кандидаты.** Один запрос на `hook_candidates` вариантов, ответ — JSON-массив
   `{"hook", "hook_type"}`. От модели требуются разные углы: минимум три разных
   `hook_type`, а не переформулировки одной мысли.
2. **Детерминированный фильтр** до всякого скоринга: приветствия, представления канала
   и анонсы темы («hi everyone», «в этом видео», «сегодня мы») режутся регуляркой,
   а также слишком короткие и длиннее 25 слов. Модель не должна уговаривать нас, что
   приветствие — хороший хук.
3. **Скорер.** Второй запрос ранжирует выживших по фиксированным критериям и возвращает
   `{"best", "reason"}`. Переписывать кандидатов ему запрещено — иначе выбранный текст
   разъедется с `hook_type`, и аналитика по классам перестанет что-либо значить.
4. **Хук пиннится в сценарий** дословно: он уезжает в runtime-часть промпта
   (`# Initialization`), а не в правила. Поэтому `custom_system_prompt` его не съедает.
5. `hook` и `hook_type` пишутся в состояние задачи — оба поля строковые и переживают
   и `MemoryState`, и `RedisState`.

## Решения

- **Фильтр раньше скорера.** Отсев мусора не должен стоить вызова модели, а критерий
  «не начинать с приветствия» — бинарный, его незачем отдавать на суждение.
- **Один выживший — скорер не зовём.** Ранжировать нечего, платить за вызов не за что.
- **Неизвестный `hook_type` не убивает хук**: текст сохраняется, класс уходит в
  `unknown`. Теряется измерение аналитики, а не ролик.
- **Провал шага деградирует, а не валит задачу.** Ошибка провайдера, нераспарсенный
  JSON или отсев всех кандидатов дают пустой результат — сценарий генерируется как
  раньше, просто без навязанной первой строки.
- **Свой сценарий пользователя шаг не трогает**: при заполненном `video_script`
  ни хука, ни генерации не происходит.

## Конфиг

```toml
script_prompt_preset = "playbook"   # шаг работает только с этим пресетом
hook_candidates = 5                 # 0 выключает шаг
```

Цена — два дополнительных вызова LLM на ролик (при одном выжившем кандидате — один).

## Чего шаг не делает

- **Не учится.** `hook_type` копится в состоянии задачи, но обратной связи
  «какой класс дал retention» нет — для неё нужна аналитика из
  `docs/playbook/publishing.md` и хранилище результатов.
- **Не проверяет фактуру** первой строки: цепочка `research → claim list → verification`
  из `docs/playbook/script.md` по-прежнему не реализована.
